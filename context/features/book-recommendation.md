# 书籍推荐｜产品 Brief

## 1. 背景

AI-Native 读书雷达当前帮助 AI 学习者和转型从业者发现具有长期价值的 AI 相关书籍。现有雷达书籍由系统预置，用户只能浏览、筛选和查看详情，暂时没有提交推荐书籍的能力。

本次增量希望让用户可以从雷达首页发起一次书籍推荐，完成必要信息填写，提交后获得明确处理结果，并能查看本次推荐记录或返回原雷达浏览位置。

推荐不会自动进入正式雷达。正式雷达仍保持专业可信和长期价值导向。

## 2. 本轮 Scope

### 本轮需要完成

1. 用户能在首页发现“推荐一本书”的能力。
2. 用户能提交一本书的推荐。
3. 用户能填写推荐所需信息。
4. 用户提交后能获得明确结果反馈。
5. 用户能通过弹窗查看本次推荐记录。
6. 用户关闭弹窗后返回雷达页面继续浏览。

### 本轮不做

- 账号体系；
- 审核后台；
- 自动收录正式雷达；
- 社区评论、点赞、关注；
- 复杂评分机制；
- 历史版本对比；
- 现有雷达主流程重构。

## 3. 已确认 To-Be Journey

1. 浏览雷达首页。
2. 发起书籍推荐。
3. 完成推荐所需信息。
4. 提交推荐。
5. 获得处理结果。
6. 默认以弹窗展示推荐记录。
7. 关闭弹窗后返回雷达页面。

## 4. 已确认业务规则

| 规则 | 内容 |
|---|---|
| 推荐对象 | 只支持书籍。 |
| 必填信息 | 书名、作者、所属领域、推荐理由、推荐指数。 |
| 所属领域 | 复用现有 8 个主题领域。 |
| 推荐指数 | 提交者个人推荐指数，不等同于正式雷达评分。 |
| 推荐理由 | 必须体现具体理由，不能只是“我喜欢”或“我推荐”。 |
| 长期价值 | 推荐理由需要体现这本书为什么具有长期阅读价值。 |
| 字数限制 | 推荐理由限制为 30-300 字。 |
| 正式雷达关系 | 推荐不会立即进入正式雷达。 |
| 推荐记录 | 提交后默认以弹窗展示全部推荐记录。 |
| 返回路径 | 用户关闭推荐记录弹窗后返回雷达页面。 |
| 持久化预期 | 推荐记录刷新页面后仍需保留，并期待通过后台数据库保存不同用户的推荐记录。 |

## 5. 与现有产品的关系

| 检查项 | 判断 |
|---|---|
| 与产品定位 | 一致。推荐能力强化“专业人群共建”和长期价值书单方向。 |
| 与首页现状 | 一致。当前首页已有“推荐一本书”入口，可作为发起点。 |
| 与正式雷达数据 | 不冲突。用户推荐记录与正式雷达书籍是两个概念。 |
| 与当前技术 Scope | 存在后续设计边界：业务上确认需要持久化和后台数据库，但此前本轮不做真实后端。进入技术设计时需明确本轮是先做前端模拟持久化，还是调整 Scope 引入后端。 |

## 6. Journey 断点

| Journey 步骤 | 当前支持情况 | 断点 |
|---|---|---|
| 浏览雷达首页 | 已支持 | 无 |
| 发起书籍推荐 | 部分支持 | 首页有按钮，但尚未连接推荐流程 |
| 完成推荐信息 | 未支持 | 缺少推荐表单和字段校验 |
| 提交推荐 | 未支持 | 缺少提交动作、保存策略、失败处理 |
| 获得处理结果 | 未支持 | 缺少成功、失败、处理中反馈 |
| 查看推荐记录 | 未支持 | 缺少推荐记录弹窗 |
| 返回雷达页面 | 未支持 | 缺少关闭弹窗后恢复浏览上下文的规则 |

## 7. 进入 UI 设计前必须补齐的业务规则

| 规则 | 为什么需要补齐 |
|---|---|
| 推荐指数输入方式 | 决定是星级、分段按钮还是数字选择。 |
| 推荐记录展示字段 | 决定弹窗内容结构。 |
| 推荐记录持久化方式 | 决定刷新后是否仍能看到记录，以及是否需要后端数据库。 |
| 提交失败场景 | 决定错误反馈文案和重试路径。 |
| 用户身份缺失时的记录归属 | 当前不做账号体系，但又期待保存不同用户记录，需要明确临时用户、匿名用户或后续账号依赖。 |

## 8. 已知事实、设计建议与待确认假设

### 已知事实

- 当前产品是面向 AI 学习者的长期价值书单与学习路径参考产品。
- 当前首页已有“推荐一本书”入口。
- 当前正式雷达书籍来自系统预置 mock 数据。
- 本次推荐只支持书籍。
- 推荐不会立即进入正式雷达。
- 推荐指数是提交者个人推荐指数，不等同于正式雷达评分。
- 推荐理由需要具体，并体现长期价值。
- 推荐理由限制为 30-300 字。
- 推荐记录需要刷新页面后仍然保存。
- 业务期待未来通过后台数据库保存不同用户的推荐记录。
- 推荐完成后默认以弹窗展示全部推荐记录，关闭后返回雷达页面。
- 个人重复书籍不允许提交。
- 未提交草稿在用户离开推荐流程后需要保留，允许下一次进入推荐时继续编辑。

### 设计建议

- 推荐流程应保持轻量，不扩展成社区投稿系统。
- 推荐成功反馈必须明确说明“已记录，但不会立即进入正式雷达”。
- 推荐记录弹窗应展示全部推荐记录，并突出刚刚提交的记录，帮助用户确认提交结果。
- 在没有账号体系前，应避免承诺“跨设备查看不同用户记录”。

### 待确认假设

- 刷新后保留推荐记录的技术方案暂不在本轮产品设计中确认，后续技术实现阶段再决定。
- 若必须保存不同用户推荐记录，则本轮 Scope 需要增加后端数据库或至少明确后端占位方案。
- “个人重复书籍”的识别口径建议为书名 + 作者完全匹配，是否需要忽略大小写、空格和中英文符号差异，后续规则设计再确认。

## 9. 改变 / 不变 / 复用 / 不做

### 改变

| 项目 | 变化 |
|---|---|
| 推荐入口 | 从静态按钮变为可进入推荐流程的入口。 |
| 用户任务流 | 新增“发起推荐 → 填写信息 → 提交 → 结果反馈 → 推荐记录弹窗 → 返回雷达”。 |
| 数据概念 | 新增“用户推荐记录”，与正式雷达书籍区分。 |
| 结果反馈 | 新增推荐成功、失败、记录展示反馈。 |
| 持久化预期 | 推荐记录需要刷新后仍然保留，并期待进入后台数据库。 |
| 重复推荐限制 | 个人重复书籍不允许再次提交。 |
| 草稿保留 | 未提交草稿离开后保留，允许下一次推荐再次进入。 |

### 不变

| 项目 | 保持不变 |
|---|---|
| 正式雷达主流程 | 继续以浏览、筛选、Hover、Click 详情为核心。 |
| 正式雷达数据 | 用户推荐不自动进入正式雷达。 |
| 八大主题领域 | 推荐所属领域继续复用现有领域。 |
| 产品定位 | 继续强调长期价值、专业可信、结构化学习路径。 |
| 本轮边界 | 不做账号、审核后台、社区和复杂评分机制，除非后续明确调整 Scope。 |

### 复用

| 项目 | 复用方式 |
|---|---|
| 首页入口 | 复用当前“推荐一本书”按钮作为发起入口。 |
| 八大领域 | 复用现有 `RadarDomain`。 |
| 推荐指数 | 复用 1-5 分语义，但标注为个人推荐指数。 |
| 基础视觉规范 | 复用 `context/ux-design-guidelines.md` 中专业、克制、编辑感风格。 |
| 基础 UI | 可复用现有按钮、标签、空态等基础组件。 |

### 不做

| 项目 | 原因 |
|---|---|
| 自动收录正式雷达 | 与“推荐不会立即进入正式雷达”冲突。 |
| 审核后台 | 超出本轮产品增量。 |
| 账号体系 | 超出本轮产品增量，但会影响不同用户记录保存，需后续单独设计。 |
| 社区评论/点赞 | 会扩展成社区产品。 |
| 复杂评分机制 | 与轻量推荐闭环无关。 |
| 现有雷达主流程重构 | 本轮只新增推荐能力，不重构首页探索体验。 |

## 10. 关键风险

| 风险 | 说明 |
|---|---|
| 持久化与无后端 Scope 冲突 | 用户已确认希望刷新后保留并期待后台数据库，但此前 Scope 不做真实后端。后续技术设计必须先决定是否调整 Scope。 |
| 个人推荐指数与正式雷达评分混淆 | 需要在提交和结果反馈中明确区分，避免用户误解。 |
| 推荐理由质量不足 | 如果不设置理由标准，推荐能力会削弱产品长期价值定位。 |
| 无账号下的不同用户记录归属 | 如果要保存不同用户记录，需要账号、匿名身份或设备标识策略。 |

## 11. UI、页面与关键交互设计

### 11.1 Journey 与页面 / 交互映射

| Journey | 页面 / 承载方式 | 用户动作 | 系统反馈 |
|---|---|---|---|
| 浏览雷达首页 | 当前首页 | 浏览雷达、筛选、查看详情 | 保持现有雷达体验 |
| 发起书籍推荐 | 首页“推荐一本书”入口 | 点击顶部或底部入口 | 打开推荐表单 |
| 完成推荐信息 | 推荐表单承载层 | 填写书名、作者、领域、推荐理由、推荐指数 | 实时校验必填项、理由字数和重复书籍 |
| 提交推荐 | 推荐表单底部操作区 | 点击提交 | 进入提交中状态，按钮不可重复点击 |
| 获得处理结果 | 推荐结果弹窗 | 查看提交结果 | 展示成功或失败反馈，并说明不会立即进入正式雷达 |
| 查看推荐记录 | 成功弹窗内 | 查看全部推荐记录 | 展示已提交推荐列表，并突出最新提交 |
| 返回浏览 | 关闭弹窗 | 关闭结果弹窗 | 返回原雷达页面，保留原浏览上下文 |

### 11.2 推荐方案

推荐采用“右侧抽屉表单 + 成功记录弹窗”。

| 设计点 | 内容 |
|---|---|
| 发起方式 | 点击“推荐一本书”后，从右侧打开推荐抽屉。 |
| 填写方式 | 抽屉内完成推荐表单。 |
| 成功反馈 | 提交成功后关闭抽屉，展示居中推荐记录弹窗。 |
| 记录展示 | 弹窗展示全部推荐记录，并突出刚提交的记录。 |
| 返回方式 | 关闭弹窗后回到原雷达浏览位置。 |
| 失败反馈 | 抽屉内显示错误提示，保留用户已填写内容。 |

推荐理由：

- 不打断雷达首页上下文，符合“关闭弹窗后返回雷达页面”的目标。
- 右侧抽屉适合桌面端表单填写，也与当前右侧详情面板的探索习惯一致。
- 成功弹窗能强化“已记录但不会立即进入正式雷达”的处理结果。
- 比独立页面更轻，不会把本轮增量扩展成完整投稿系统。
- 比小弹窗表单更适合填写 30-300 字的推荐理由。

### 11.3 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 独立推荐页面 | 空间充足，流程清晰 | 容易扩展成二级页面体系，返回原浏览状态更复杂 | 不推荐 |
| 居中弹窗表单 | 实现轻，入口明确 | 推荐理由较长时空间拥挤，移动端体验差 | 不推荐 |

### 11.4 推荐入口

| 入口位置 | 设计方式 |
|---|---|
| 顶部导航“推荐一本书” | 作为主入口，保持主按钮。 |
| 底部辅助入口卡“推荐一本书” | 作为二次入口，文案强调“推荐具有长期价值的 AI 书籍”。 |

入口点击后打开推荐抽屉，不跳转页面。

### 11.5 推荐抽屉结构

推荐抽屉从页面右侧打开，背景保留雷达首页但降低干扰。

| 区域 | 内容 |
|---|---|
| 抽屉标题 | 推荐一本 AI 书籍 |
| 说明文案 | 你的推荐会被记录，但不会立即进入正式雷达 |
| 表单主体 | 书名、作者、所属领域、推荐指数、推荐理由 |
| 质量提示 | 推荐理由需说明长期价值、适合谁读、解决什么学习问题 |
| 操作区 | 取消、提交推荐 |

字段设计：

| 字段 | 交互建议 |
|---|---|
| 书名 | 单行输入，必填。 |
| 作者 | 单行输入，必填。 |
| 所属领域 | 使用八大领域单选，不允许自定义领域。 |
| 推荐指数 | 使用 1-5 分分段选择或星级选择，标注“个人推荐指数”。 |
| 推荐理由 | 多行输入，必填；限制 30-300 字；显示字数计数和质量提示。 |

推荐理由提示文案：

```text
请说明这本书为什么具有长期价值，适合什么阶段的人阅读，以及它能帮助解决什么学习问题。
```

### 11.6 表单校验

提交按钮可用条件：

- 书名非空；
- 作者非空；
- 所属领域已选择；
- 推荐指数已选择；
- 推荐理由在 30-300 字之间；
- 当前个人推荐记录中不存在同一书名 + 作者的推荐。

| 场景 | 表现 |
|---|---|
| 初始状态 | 提交按钮禁用或弱化，提示必填项。 |
| 必填缺失 | 字段下方显示短错误提示。 |
| 推荐理由少于 30 字 | 提示“请补充长期价值、适合人群或阅读收获”。 |
| 推荐理由超过 300 字 | 提示“推荐理由过长，请压缩到 300 字以内”。 |
| 推荐指数未选择 | 提示“请选择你的个人推荐指数”。 |
| 领域未选择 | 提示“请选择一个最匹配的领域”。 |
| 个人重复书籍 | 提示“你已经推荐过这本书，本次无需重复提交”。 |

个人重复书籍的默认识别口径为书名 + 作者。更精细的大小写、空格、符号归一规则进入后续规则设计确认。

### 11.7 草稿保留

用户未提交就关闭抽屉或离开推荐流程时，应保留未提交草稿。

| 场景 | 表现 |
|---|---|
| 用户关闭未提交表单 | 保留已填写内容。 |
| 用户再次点击推荐入口 | 重新打开抽屉并恢复上次草稿。 |
| 用户成功提交 | 清空当前草稿。 |
| 用户主动清空表单 | 清空草稿。 |

草稿保留的具体技术方案不在本轮 UI 设计中确认。

### 11.8 提交中状态

| 元素 | 表现 |
|---|---|
| 提交按钮 | 显示“提交中…”并禁用。 |
| 表单字段 | 保留内容，不清空。 |
| 取消按钮 | 可禁用，避免提交过程中状态混乱。 |
| 页面背景 | 保持抽屉打开。 |

提交中不使用全屏 loading，避免流程显得过重。

### 11.9 成功反馈与推荐记录弹窗

提交成功后：

1. 关闭推荐抽屉。
2. 打开居中弹窗。
3. 弹窗标题为“推荐已记录”。
4. 明确提示“这条推荐不会立即进入正式雷达，后续会作为候选记录处理”。
5. 展示全部推荐记录，并突出刚提交的记录。

推荐记录弹窗字段：

| 字段 | 展示方式 |
|---|---|
| 书名 | 主标题 |
| 作者 | 次级信息 |
| 所属领域 | 标签 |
| 个人推荐指数 | 分数或星级，并标注不是正式雷达评分 |
| 推荐理由 | 展示完整理由或摘要展开 |
| 记录状态 | 已记录，待后续处理 |
| 提交时间 | 展示本次提交时间 |

弹窗操作：

| 操作 | 结果 |
|---|---|
| 关闭 | 返回雷达首页，保留原浏览状态。 |
| 再推荐一本 | 关闭弹窗并重新打开空表单。 |
| 查看全部推荐记录 | 默认已在弹窗内展示全部推荐记录，不另开页面。 |

### 11.10 失败反馈

失败反馈不跳转、不清空表单。

| 失败类型 | 表现 |
|---|---|
| 表单校验失败 | 字段级错误提示。 |
| 保存失败 | 抽屉顶部显示轻量错误条。 |
| 未知异常 | 显示“推荐暂未保存，请稍后重试”。 |

失败后用户可以修改内容重新提交，也可以取消并返回雷达。

### 11.11 与原浏览流程衔接

推荐流程打开前，应保留用户当时的雷达浏览状态：

| 状态 | 返回后是否保留 |
|---|---|
| 当前筛选条件 | 保留 |

### 14.0 前端落点（已确认）

| 文件 | 原因 |

### 14.1 冲突与边界

| 项目 | 已确认产品 / UX | 当前技术基线 | 判断 |
|---|---|---|---|
| 推荐记录持久化 | 刷新后仍保留，未来期待后台数据库保存不同用户记录 | 当前只有本地 Mock JSON + mock service，没有真实后端、账号体系或数据库 | 不冲突，但本轮技术设计必须先定义为“前端持久化过渡方案”或“等待后端设计后再做” |
| 用户身份 | 期待保存不同用户推荐记录 | 本轮不做账号体系 | 当前无法真正区分不同用户，只能用本地设备/浏览器维度过渡 |
| 推荐记录弹窗 | 展示全部推荐记录 | 当前没有推荐记录数据结构 | 需要新增独立推荐记录模型，不复用正式雷达 `BookItem` |
| 重复推荐 | 个人重复书籍不允许提交 | 当前没有个人记录概念 | 需要新增去重规则，默认按书名 + 作者 |

建议本轮技术草案采用：前端本地持久化作为无后端阶段的过渡，接口形态保留 service 层，未来替换为后端数据库。

### 14.2 数据模型与状态说明

推荐记录不应复用正式雷达 `BookItem`，因为它不会进入正式雷达，也没有雷达点位、圈层坐标、正式评分等字段。

建议新增表单草稿模型：

```ts
type BookRecommendationDraft = {
  title: string;
  author: string;
  domain: RadarDomain | "";
  personalScore: number | null;
  reason: string;
};
```

建议新增已提交记录模型：

```ts
type BookRecommendationRecord = {
  id: string;
  title: string;
  author: string;
  domain: RadarDomain;
  personalScore: number;
  reason: string;
  status: "recorded";
  submittedAt: string;
};
```

建议新增提交状态：

```ts
type RecommendationSubmitState =
  | "idle"
  | "editing"
  | "submitting"
  | "success"
  | "error";
```

建议新增校验错误类型：

```ts
type RecommendationValidationErrors = Partial<{
  title: string;
  author: string;
  domain: string;
  personalScore: string;
  reason: string;
  duplicate: string;
}>;
```

字段规则：

| 字段 | 规则 |
|---|---|
| `title` | 必填，去除首尾空格后不能为空 |
| `author` | 必填，去除首尾空格后不能为空 |
| `domain` | 必填，必须是现有 `RadarDomain` |
| `personalScore` | 必填，范围 1-5 |
| `reason` | 必填，30-300 字 |
| `status` | 当前只有 `recorded`，不引入审核状态 |
| `submittedAt` | 提交时生成，用于记录弹窗展示 |

### 14.3 重复推荐规则

当前默认规则：

- 同一用户记录中，`title + author` 重复则不允许再次提交。
- 初版建议做基础归一化：去除首尾空格、转小写、合并连续空格。
- 暂不做复杂同义书名、译名、ISBN 识别。

用户影响：能避免同一个人反复提交同一本书，但不会过度拦截不同译本或复杂书名差异。

### 14.4 页面状态

新增推荐相关状态应独立于雷达主流程状态：

| 状态 | 用途 |
|---|---|
| `isRecommendationDrawerOpen` | 控制右侧推荐抽屉 |
| `isRecommendationRecordsModalOpen` | 控制推荐记录弹窗 |
| `recommendationDraft` | 保存未提交草稿 |
| `recommendationRecords` | 保存全部推荐记录 |
| `latestSubmittedRecommendationId` | 高亮刚提交记录 |
| `submitState` | 控制提交中、成功、失败 |
| `validationErrors` | 字段级错误 |

不应把推荐表单状态混入 `RadarFilterState` 或 `RadarViewState`，避免破坏雷达筛选、Hover、Click 逻辑。

### 14.5 接口和数据访问建议

建议新增独立 service：

```text
src/services/recommendationsService.ts
```

职责：

| 方法 | 用途 |
|---|---|
| `getRecommendationRecords()` | 获取全部推荐记录 |
| `saveRecommendationRecord(record)` | 保存一条推荐记录 |
| `getRecommendationDraft()` | 获取未提交草稿 |
| `saveRecommendationDraft(draft)` | 保存草稿 |
| `clearRecommendationDraft()` | 提交成功或用户主动清空时删除草稿 |

本轮数据访问建议：

- 推荐记录保存到浏览器本地存储；
- 草稿也保存到浏览器本地存储；
- 所有读写都封装在 `recommendationsService.ts`；
- UI 组件不直接访问 `localStorage`；
- 未来接后台数据库时，替换 service 实现，不改 UI 组件边界。

未来后端数据库可复用同一 service 接口语义：

- `getRecommendationRecords()` 从本地存储改为请求 API；
- `saveRecommendationRecord()` 从本地写入改为 POST；
- 草稿是否后端保存另行决定；
- 如果引入账号体系，再把用户身份绑定放在 service/API 层，而不是 UI 层。

### 14.10 异常、重复推荐和边界情况

| 场景 | 处理 |
|---|---|
| 必填缺失 | 字段级错误提示，禁止提交 |
| 理由不足 30 字 | 提示补充长期价值、适合人群或阅读收获 |
| 理由超过 300 字 | 提示压缩内容 |
| 重复书名 + 作者 | 禁止提交，提示已推荐过 |
| 保存失败 | 保留草稿，允许重试 |
| 用户关闭抽屉 | 保留草稿 |
| 用户成功提交后再推荐 | 打开空表单 |
| 推荐记录为空 | 弹窗不应出现；如未来有记录入口，则显示空态 |
| 移动端空间不足 | 使用全屏表单和全屏结果弹层 |
| 本地存储不可用 | 进入保存失败状态，提示暂未保存 |

### 14.11 风险、待确认项和验收标准

#### 风险

| 风险 | 说明 |
|---|---|
| 技术持久化方案未确认 | 产品要求刷新后保留，但用户希望后续再询问技术实现 |
| 无账号无法区分不同用户 | 当前本轮不做账号，无法真正实现跨用户数据库记录 |
| 本地存储与未来后端迁移差异 | 后续 API 可能需要调整 record 字段 |
| 重复判断过粗 | 书名 + 作者可能无法识别译名、大小写、标点差异 |
| 记录弹窗信息过多 | 全部推荐记录增多后弹窗可能拥挤，需要滚动或分组 |

#### 待确认项

| 问题 | 建议默认 |
|---|---|
| 推荐指数输入方式 | 1-5 分分段按钮，清晰且便于移动端点击 |
| 推荐记录展示排序 | 最新提交在最上方 |
| 推荐记录过多时处理 | 弹窗内滚动，不新增页面 |
| 重复判断归一化 | 去首尾空格、忽略大小写、合并连续空格 |
| 本轮持久化技术 | 等后续技术实现阶段确认 |

#### 最小可用版本验收标准

1. 用户能从首页点击“推荐一本书”打开推荐表单。
2. 用户能填写书名、作者、领域、个人推荐指数和 30-300 字推荐理由。
3. 缺失字段、理由字数不合规、重复推荐时不能提交，并有明确提示。
4. 提交成功后展示推荐记录弹窗，弹窗内包含全部推荐记录，并突出最新提交。
5. 推荐成功反馈明确说明不会立即进入正式雷达。
6. 关闭弹窗后返回雷达页面，原筛选和选中状态不被破坏。
7. 未提交草稿在离开推荐流程后可恢复。
8. 正式雷达书籍、筛选、Hover、Click 详情不受影响。
9. 桌面端和移动端都能完成推荐流程。
10. 不引入新依赖，不重构全站，不修改正式雷达数据模型。
